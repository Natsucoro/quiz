## 0. エグゼクティブサマリー（朝イチで読むならここだけ）

**イントロベット**は、オリジナル楽曲のイントロを聴いて「この曲の歌詞にどのワードが出てくるか」を予想し、
ゲーム内コインを賭け合う、スマホ持ち寄り型のパーティーゲームです。

- ホストが部屋を作り、参加者は自分のスマホから入室（Jackbox方式）
- イントロが流れる十数秒のあいだに、提示された6つのワードへコインをベット
- 歌詞が明かされ、当たったワードに賭けた人がコインを獲得
- 全ラウンド終了後、**コインが一番多い人の勝ち**

**このゲームの背骨は「歌手キャラのクセを覚えるほど強くなる」こと**です。
楽曲はすべてなつみさんの自作（Suno）なので、架空の歌手キャラごとに歌詞の語彙をコントロールでき、
「この歌手ならこのワードを歌いそう」という読みが、そのまま勝率に直結します。

**朝いちばんに決めてほしいこと3つ**（詳細は §11）
1. リポジトリ作成（Claudeには権限がないため手動。手順は §12）
2. 課金の価格設定（人数上限解放をいくらにするか）
3. 「同じ部屋に集まって遊ぶ」前提でMVPを作ってよいか（オンライン別室対応は後回しにしたい）

## 1. コンセプト

### 1.1 ひとことで言うと
> **イントロだけを聴いて、歌詞を当てにいくベッティングゲーム。**

### 1.2 既存ゲームとの違い
いわゆる「イントロドン」は**曲名を当てる**ゲームで、知識量がそのまま勝敗になります。
イントロベットは**曲名ではなく歌詞の中身に賭ける**ので、

- 曲を知っている人 → ほぼ確実に当てられる（やり込みの報酬）
- 曲を知らない人 → 歌手のキャラ・曲の雰囲気から山を張れる（初見でも勝負になる）
- しかも**賭け方**という第二の軸がある → 知識で劣る人が大穴一点張りで逆転できる

この「知識」と「賭け」の二重構造により、**知識差があっても最後まで誰が勝つか分からない**ゲームになります。

### 1.3 ターゲット
- 友達・家族で集まったときに、スマホだけで遊べるパーティーゲームを探している人
- 2〜10人程度のグループ
- 音楽の知識は不要（既存曲を使わないので、むしろ全員が初心者スタート）

### 1.4 「既存曲を使わない」ことが最大の強み
一般的な音楽ゲームは楽曲の権利処理が最大の壁ですが、本作は**全楽曲がなつみさんのオリジナル**です。これにより:

| 項目 | 効果 |
|---|---|
| 権利処理 | 不要。アプリ内でそのまま音源を流せる |
| 歌詞の語彙 | **こちらで設計できる** → ゲームバランスを作品側で調整可能 |
| 難易度調整 | レア語を仕込む／頻出語を散らす、を意図的にできる |
| 公平性 | 誰も元曲を知らない状態から始まる。音楽に詳しい人だけが勝つゲームにならない |
| バージョン違い | Sunoは1生成で2テイク作るので、同一歌詞・別アレンジが自然に手に入る |

## 3. ゲームルール詳細

### 3.1 プレイ人数【確定】
| プラン | 人数 |
|---|---|
| 無料 | **2〜4人** |
| 有料 | **2〜10人** |

- ホストを含めた人数です。
- **課金するのはホストだけでよい**設計にします（§8参照）。参加者は常に無料で入れます。

### 3.2 ゲームの長さ【確定】
設定で選択できます。

| モード | 曲数 | 目安時間 |
|---|---|---|
| さくっと | 5曲 | 約8分 |
| じっくり | 10曲 | 約15分 |

### 3.3 コイン【確定】
- **ゲーム内通貨のみ。現金への換金・他ユーザーへの譲渡は一切できません。**
  （利用規約に明記します。これが賭博に該当しないことの根拠になります → §10）
- 全員 **1,000コイン** からスタート。

### 3.4 ベット【確定】
- **分散ベット可能。どのワードにいくら賭けるかは完全に個人の自由。**
  - 例: 「君」に300、「流星」に100、残り600は温存 —— も可
- **賭けるなら、最低ベット額は現在の持ちコインの10%**（切り上げ、最低10コイン）【提案】
  - ちまちま賭けて何も起きない展開を防ぐための下限です。
- 上限は現在の持ちコイン全額（オールイン可）。
- **パス（何も賭けない）は可能**。時間切れも同じくパス扱いで、コインは増減しません。
  - なつみさんの「見送りアリ／ナシ」の判断はまだ聞けていないため、暫定でパス可としています（未決事項 #4）。
  - もしパスを禁止したい場合は「最低1ワードへのベットを必須」に切り替えます。

### 3.5 持ちコインが0になったら【提案】
パーティーゲームで脱落者が出ると場が白けるため、**脱落はさせません**。

- 0コインになったプレイヤーは、次ラウンド開始時に **100コインを自動補給**
- ただし補給回数は記録し、**最終順位の同点タイブレーク**に使う（補給が少ない人が上位）

### 3.6 同点だった場合【提案】
最終コインが同数のときは、以下の順で順位を決めます。

1. **0コイン補給を受けた回数が少ない**プレイヤーが上位
2. それでも同点なら、**的中したベットの本数が多い**プレイヤーが上位
3. それでも同点なら、**同着**とする

### 3.7 最終ラウンドの逆転要素【提案】
最終ラウンドのみ **全倍率が2倍（ダブルアップラウンド）**。
最下位のプレイヤーにも数学的な逆転可能性が残り、最後まで全員が真剣になります。

### 3.8 ベットの可視性【確定】
設定で切り替えられます。

| モード | 内容 |
|---|---|
| **シークレット（デフォルト）** | 誰が何に賭けたか、締切まで分からない |
| オープン | 全員のベット状況がリアルタイムで見える。読み合い・心理戦モード |

なつみさんの意向により**デフォルトはシークレット**です。

---

### 3.9 その他の進行ルール【提案】

レビューで抜けが見つかった項目です。実装前に必ず決めておく必要があります。

| 項目 | 決定 |
|---|---|
| **同じ曲の重複出題** | **1ゲーム内で同じ曲は絶対に出さない**。バージョン違いのペアは別曲扱いなので出てよい |
| **ラウンドの進行** | 結果表示後5秒で自動的に次へ。ホストは手動で「次へ」を押して早送りもできる |
| **途中参加** | **不可**。ロビー段階でのみ入室できる。開始後に来た人は次のゲームから |
| **途中退出** | 残ったプレイヤーだけでゲームは続行。退出者のコインは順位表に残す |
| **切断・再接続** | 同じ端末から自動的に元のプレイヤーとして復帰できる。切断中のラウンドはパス扱い |
| **参加コードの衝突** | 6桁コードは発行時に使用中の部屋と重複しないか必ず検査する |
| **部屋の寿命** | 最終操作から2時間で自動的に破棄する |

## 4. 候補ワードと倍率（本作の心臓部）

ここが最も設計が難しく、最も面白さを左右する部分です。壁打ちで議論した結論をまとめます。

### 4.1 大原則：倍率は「全曲コーパス基準」で計算する【確定】

ワード倍率を**その歌手だけの出現率**で計算してはいけません。
なぜなら「この歌手は"海"をよく歌う」という知識がすでに倍率に織り込まれてしまい、
**歌手を覚えても儲からなくなる**からです。

したがって:

> **倍率は、登録されている全楽曲をまとめた出現率から計算する。**

これにより、「全体では"海"はレアで10倍だが、この歌手に限っては頻出」という
**歪み（＝プレイヤーの取り分）**が生まれます。歌手を覚えた人だけがそれを刈り取れます。
これが本作の"やり込み報酬"の正体です。

### 4.2 ワードの階層（ティア）【提案】

ワード w の出現率を
`p(w) = (w を歌詞に含む曲数) ÷ (登録楽曲の総数)`
と定義します。

ティアの境界は**絶対値ではなく辞書内のパーセンタイルで定義**します。
楽曲が増えるにつれて出現率の分布は変わるため、絶対値で固定すると必ず破綻するからです。

| ティア | 辞書内の位置 | 出現率の目安 | 例（イメージ） | UI色 |
|---|---|---|---|---|
| **堅い (Common)** | 上位20% | 35〜60% | 君、心、夜 | 青 |
| **中間 (Uncommon)** | 20〜50% | 15〜35% | 涙、季節、約束 | 緑 |
| **穴 (Rare)** | 50〜85% | 5〜15% | 流星、硝子、逆光 | 橙 |
| **大穴 (Jackpot)** | 下位15% | 2〜5% | 蜃気楼、極光 | 赤（レア演出付き） |

---

### 4.3 候補ワードの提示アルゴリズム【提案】

1ラウンドあたり **6個** を提示します。

```
STEP 1: 候補6個を「曲を一切見ずに」辞書からティア別に抽出する
          堅い 2個 / 中間 2個 / 穴 2個
          （30%の確率で、穴1枠を「大穴」1枠に置き換える）

STEP 2: 抽出した6個のうち、その曲の歌詞に実在するものが自動的に「正解」になる
          → 正解を意図的に作らない。歌詞との一致は"たまたま"で決まる

STEP 3: 正解が2個未満だったら、STEP 1 からやり直す（引き直し）
          → これが「全滅回を作らない」保証（なつみ確定事項）
          → 平均1.9回の引き直しで成立するので、処理は一瞬で終わる
          → 50回引き直しても成立しない曲（歌詞のワードが極端に少ない）は、
            フォールバックとして歌詞のワードを直接1〜2個ねじ込む

STEP 4: シャッフルして提示
```

**このアルゴリズムの要点は STEP 1 の「曲を見ずに引く」ことです。**
候補を先に決め、正解は歌詞との偶然の一致に任せる。
こうすると各ワードの正解率が**その語の本来の出現率にきわめて近くなる**ため、
倍率が素直に「レアなほど高い」構造になります。

---

### 4.4 やってはいけない設計（重要）

#### ❌ NG-1: 「各ティアに必ず正解を1つ入れる」

壁打ちで一度「各倍率帯に最低1〜2個」という話が出ましたが、
これを **"各ティアに正解を1つずつ保証する"** と解釈して実装するとゲームが壊れます。

> 穴枠（仮に6倍）に必ず正解が含まれるなら、**全員が毎回穴枠だけに賭ければ必勝**です。
> 倍率が意味を失い、読み合いも歌手のクセも全部無意味になります。

#### ❌ NG-2: 「正解ワードを、その曲の歌詞から先に抜き出して枠に詰める」

これが Ver.0.1 で書いていた方式で、**シミュレーションで破綻が確認されたため差し替えました。**

歌詞から正解を先に抜くと、レアワードは「歌詞に入っている」時点で高確率に選ばれてしまい、
**表示されたレアワードの正解率が跳ね上がります。** 実測結果は以下のとおりです。

| ティア | ❌ 歌詞から抜く方式 | ✅ 採用した v0.2 |
|---|---|---|
| 堅い | 1.8倍 | 1.5倍 |
| 中間 | 2.4倍 | 2.5倍 |
| 穴 | 4.2倍 | 6.2倍 |
| **大穴** | **7.5倍** | **17.3倍** |

歌詞から抜く方式では**大穴が7.5倍まで落ち込み**、
「めったに出ないワードを当てて大逆転」という本作最大の見せ場が消えてしまいます。

#### ✅ 正しい考え方

> **正解のティア分布は「その曲の歌詞が持つ性質」に自然に任せる。**

- レア語を多用する歌手の曲 → 穴が当たりやすい回になる
- 平易な言葉で歌う歌手の曲 → 堅いのしか当たらない回になる

つまり **「歌手のクセ」がそのまま「今回穴を狙うべきか」の判断材料になります。**
4.1の全曲基準の倍率と組み合わさることで、歌手を覚えた人が最大の利益を得る構造が完成します。

### 4.5 倍率の算出方法【提案】

「正解2個以上」の引き直しをかけている以上、
**素の出現率 p(w) をそのまま 1/p して倍率にすることはできません。**
引き直しによって、表示されたワードの正解率は本来の出現率より押し上げられるからです。

そこで、**実際の提示アルゴリズムを通したときの「表示されたワードが正解である確率」を実測して倍率を決めます。**

```
【ビルド時に実行するスクリプト】
1. §4.3 の提示アルゴリズムを、全楽曲 × 200,000ラウンドぶんシミュレーションする
2. ワード w について
     q(w) = (w が表示され、かつ正解だった回数) ÷ (w が表示された回数)
   を実測する
3. 倍率(w) = (1 - 控除率) ÷ q(w)   ※小数第1位に丸め
4. 結果を静的JSONに書き出し、アプリはそれを読むだけにする
```

**控除率は MVP では 0%**【提案】とします（賭け全体の期待値がちょうど1になる）。
ランダムに賭ける人は増えも減りもせず、歌手を読める人だけがプラスになります。
将来ゲームを引き締めたくなったときのために、5%程度の控除を入れるツマミとして残しておきます。

#### 倍率の実測値（200,000ラウンドのシミュレーション結果）

> この数値は `scripts/simulate-odds.py` を実行すれば再現できます。
> ```
> python3 scripts/simulate-odds.py                  # 正解2個以上を保証（採用案）
> python3 scripts/simulate-odds.py --min-correct 1  # 正解1個以上を保証（比較用）
> ```


| ティア | 表示時の正解率 | **倍率** |
|---|---|---|
| 堅い | 67.9% | **1.5倍** |
| 中間 | 39.2% | **2.5倍** |
| 穴 | 16.2% | **6.2倍** |
| 大穴 | 5.8% | **17.3倍** |

- 1ラウンドの平均正解数: **2.44個**
- 正解数の分布: **2個 64% / 3個 29% / 4個 6%**
  → 93%のラウンドで正解は2〜3個。なつみさんの「難しすぎる」という懸念は解消されています
- 適当に賭けても **約4割** は当たります

> ⚠️ この数字は「典型的な歌詞のワード構成」を仮定した推定値です。
> 実際の楽曲が30曲ほど登録された時点で必ず再計算し、体感と突き合わせて調整してください。

#### 調整用のツマミ：正解保証の個数【要決定 ⚠️】

「正解を何個以上保証するか」で、ゲームの手触りが大きく変わります。

| 保証 | 倍率の幅 | 正解数の分布 | 手触り |
|---|---|---|---|
| **2個以上（採用）** | 1.5〜17.3倍 | 2個64% / 3個29% | **当てやすい。パーティー向き** |
| 1個以上 | 1.8〜25.0倍 | 1個39% / 2個39% / 3個18% | 倍率に夢があるが、当てにくい |

なつみさんの「正解が少なすぎると難しすぎる」という意向に沿って **2個以上を採用**しました。
ただし「もっとヒリつく方がいい」と感じたら、1個以上に切り替えるだけで難易度を上げられます。
**設定値ひとつで切り替わるよう実装します。**

### 4.6 正解判定とワードの正規化【提案】

日本語歌詞は表記ゆれが激しいため、判定ロジックが甘いと必ず揉めます。

- 「愛」と「愛して」「愛してる」は**同じワードとして扱う**（語幹一致）
- 「君」と「キミ」「きみ」は**同じワードとして扱う**（かな/カナ/漢字ゆれ吸収）
- 判定は**曲データ登録時に確定させる**（実行時に解析しない）
  - 歌詞を登録する際、その曲が含むワードIDの配列を事前計算して保存
  - 形態素解析は kuromoji.js をビルド時に使用、最終的に**人の目で確認**する
  - → クイズ集アプリと同じ「ビルド時生成 + 静的JSON」の思想を踏襲

## 5. 歌手キャラクター【確定】

### 5.1 基本方針
- 歌手は**すべて架空のキャラクター**
- 実在の歌手の**作風をオマージュした"タイプ"**として設計する
  （例: 「昭和のきらびやかなスター歌手」タイプ）
- 各キャラに**複数曲**が紐づき、「この人ならこういう曲を歌うだろう」と予想できるようにする
- 性格・世界観をしっかり設定し、**歌詞の語彙に一貫性**を持たせる

### 5.2 権利上の注意（重要）
実在歌手の**作風のオマージュ自体は法的に問題ありません**（曲の"雰囲気"に著作権はないため）。
ただし以下の2点は必ず守ってください。

| ❌ やってはいけない | ✅ 安全な範囲 |
|---|---|
| 実名をもじって本人と誤認されるレベルの名前 | 明確に別人と分かる名前 |
| AI音声で本人の声質に似せる | 作風・ジャンル・歌い回しのオマージュに留める |

**「特定の誰か」ではなく「あのカテゴリの歌手っぽい人」**というパロディにしておけば、
誰も傷つけずに面白さだけを取れます。詳細は `docs/歌手キャラクター設計ガイド.md` に。

### 5.3 初期ラインナップ【提案】
- **8〜12キャラ**でスタート
- 1キャラあたり **5〜10曲**
- → 合計 50〜100曲。これだけあれば「クセを覚える」体験が成立します

キャラが多すぎると覚えきれず、少なすぎるとすぐ飽きます。8〜12が体感のスイートスポットです。

## 6. バージョン違い楽曲【確定】

Sunoは1回の生成で**2テイク**を出力するため、**歌詞が同じでアレンジが違う曲**が自然に手に入ります。
これをゲームに組み込むと、知識レイヤーが2段構えになります。

1. **歌手のクセを覚える** → 「このキャラなら"夜"を歌いそう」
2. **曲そのものを覚える** → 「このメロディ、前に聴いたやつの別バージョンだ！歌詞はもう知ってる」

②を引き当てたプレイヤーはほぼ確実に大勝ちできるため、やり込みへの強烈なご褒美になります。

### 6.1 出現率の制限【提案】
バージョン違いの出現率が高すぎると**単なる記憶ゲー**になります。

> **バージョン違いペアの出題は、全ラウンドの 10〜20% 程度に抑える。**

### 6.2 発展案：歌詞改変バージョン【提案・将来】
歌詞を**一部だけ変えた**バージョンを稀に混ぜると、
「知ってるつもりで賭けたら罠だった」という展開が作れます。
常連ほど悔しがる仕掛けですが、やりすぎると理不尽なので**MVPでは実装しません**。

イントロの十数秒で操作を完了させる必要があるため、**タップ数を最小に**します。

```

│  🎤 四浅見レイジ          │  ← 歌手キャラ（クセを思い出す手がかり）
│  残り時間 ████████░░ 8秒   │  ← 常に見える
│  所持: 1,000 コイン        │
├──────────────────────────┤
│  賭ける額を選ぶ            │
│  [ 50 ][ 100 ][ 300 ][ ALL ] │  ← ①額を1タップで選択
├──────────────────────────┤
│  ┌────────┐ ┌────────┐  │
│  │  君    │ │  涙    │  │  ← ②ワードを1タップで確定
│  │ 1.5倍  │ │ 2.5倍  │  │
│  └────────┘ └────────┘  │
│  ┌────────┐ ┌────────┐  │
│  │  流星  │ │  硝子  │  │
│  │ 6.2倍  │ │ 6.2倍  │  │
│  └────────┘ └────────┘  │
│  ┌────────┐ ┌────────┐  │
│  │  蜃気楼│ │  心    │  │
│  │ 17.3倍✨│ │ 1.5倍  │  │
│  └────────┘ └────────┘  │

- **2タップで1ベット完了**（額を選ぶ → ワードを押す）

それでも足りない曲のために、曲データに `bettingWindowSec` を持たせ、
**イントロ長とは独立にベット時間を設定できる**ようにしておきます（既定15秒）。

| A | 人数上限解放（買い切り） | 480〜980円 |

## 9. 技術設計【提案】

### 9.1 技術スタック
クイズ集アプリと同じ構成を選びます。**開発チームが慣れている**ことが最大の理由で、
立ち上げ速度と品質が両方取れます。

| レイヤ | 採用 | 理由 |
|---|---|---|
| フロント | React 18 + TypeScript + Vite | クイズ集と同一。資産と知見を流用 |
| 状態管理 | Zustand | 同上 |
| リアルタイム同期 | **Firebase Realtime Database** | 部屋の状態を頻繁に小さく更新する用途に最適。Firestoreより低レイテンシ・低コスト |
| 永続データ | Firestore | ユーザー、購入履歴、戦績 |
| 認証 | Firebase Auth（匿名 + Google） | 参加者は匿名で即入室、ホストはGoogleログイン |
| 音源配信 | Firebase Storage + CDN | |
| 決済 | Stripe | クイズ集と同一 |
| ホスティング | Firebase Hosting | クイズ集と同一 |

> **補足**: リアルタイム同期に Realtime Database と Firestore を使い分ける構成です。
> 「進行中の部屋の状態」は揮発的で更新が多いので RTDB、
> 「購入履歴や戦績」は永続的で検索したいので Firestore、という分担です。

### 9.2 音楽再生の同期について（重要な技術判断 ⚠️）

各自のスマホで**同時に同じ音楽を鳴らす**のは、実は難易度が高い課題です。

| 方式 | 内容 | 難易度 |
|---|---|---|
| **A. ホスト端末のみ再生** | ホストのスピーカーから流す。全員同じ部屋にいる前提 | 低 |
| B. 各自の端末で同期再生 | 事前ロード + サーバー時刻で同時再生。ズレ200ms程度は許容 | 中〜高 |

**MVPでは A を推奨します。**

理由:
- ホストが部屋を作って集まる形式＝**同じ場所にいる前提**なので、Aで要件を満たせる
- 各端末で鳴らすと、音量差・スピーカー品質差・再生ズレで**むしろ体験が悪化**する
- モバイルブラウザの自動再生制限を回避する実装が不要になり、開発速度が上がる
- Jackbox Party Pack など、成功しているスマホ持ち寄り型ゲームはすべてこの方式

Bは「離れた友達とオンラインで遊びたい」という要望が出てから Phase 3 以降で対応します。
その際も、曲を事前ロードしてサーバー時刻で同時スタートさせれば実現可能です（設計は塞ぎません）。

→ **この判断でよいか、朝に確認をください。**

### 9.3 データモデル

```typescript
// 歌手キャラクター
interface Artist {
  id: string;
  name: string;              // 表示名（架空）
  avatarUrl: string;
  era: string;               // 「昭和スター」「平成ロック」など
  personality: string;       // 性格・世界観の説明（プレイヤーに見せる）
  motifWords: string[];      // 得意ワード（内部データ。バランス調整用、非公開）
  debutOrder: number;
}

// 楽曲
interface Song {
  id: string;
  title: string;
  artistId: string;
  audioUrl: string;
  introDurationSec: number;    // イントロの実測長
  bettingWindowSec: number;    // ベット時間（既定15秒）
  lyrics: string;              // 全歌詞（結果表示用）
  wordIds: string[];           // ★この曲に含まれる辞書ワードID（事前計算）
  versionGroupId?: string;     // バージョン違いのペアを束ねるID
  versionLabel?: string;       // 「バラードVer.」など
}

// ワード辞書
interface Word {
  id: string;
  surface: string;             // 表示文字列「流星」
  aliases: string[];           // 表記ゆれ「りゅうせい」「リュウセイ」
  appearanceRate: number;      // p(w) 全曲基準の出現率
  tier: 'common' | 'uncommon' | 'rare' | 'jackpot';
  odds: number;                // シミュレーションで算出した倍率
}

// 部屋（Realtime Database）
interface Room {
  id: string;                  // 6桁の参加コード
  hostUid: string;
  status: 'lobby' | 'playing' | 'finished';
  settings: {
    roundCount: 5 | 10;
    revealBets: boolean;       // false = シークレット（既定）
    maxPlayers: number;        // 4 (無料) or 10 (有料)
  };
  players: Record<string, Player>;
  currentRound?: Round;
  roundHistory: Round[];
}

interface Player {
  uid: string;
  nickname: string;
  coins: number;
  bailoutCount: number;        // 0コイン補給を受けた回数（タイブレーク用）
  isConnected: boolean;
}

interface Round {
  index: number;
  songId: string;
  candidateWordIds: string[];        // 提示した6ワード
  correctWordIds: string[];          // うち正解だったもの
  oddsSnapshot: Record<string, number>;  // 提示時の倍率（後から変わっても記録が残る）
  bets: Record<string, Record<string, number>>;  // uid → wordId → 賭け金
  startedAt: number;
  closesAt: number;
  isDoubleUp: boolean;               // 最終ラウンドフラグ
}
```

### 9.4 不正防止
- 候補ワードの**正解情報はクライアントに送らない**。締切後にサーバー（Cloud Functions）が開示する
- ベットの締切判定は**サーバー時刻**で行う（端末時計をいじられても効かない）
- コインの増減計算はすべてサーバー側。クライアントは表示のみ
