# 楽譜カメラアプリ — 実装計画 (Ver. 1.0)

**前提**: `技術検証レポート_M0.md` の検証結果に基づく。数値の根拠はすべてそちらにある。

---

## 1. 製品像

> **紙の楽譜を撮る → 直す → 好きなキーに変える → 聴いて確かめる → 印刷する**

M0の検証により、「撮ったら全自動で移調済み楽譜が出てくる」は不可能と判明した。
音高は90〜100%読めるが、音価は複雑な曲で74%、拍子記号は必ず脱落する。
したがって **「人が直す」工程を隠さず、むしろ気持ちよくする** のがこのアプリの設計思想になる。

**主な用途**（なつみの想定）: 歌の伴奏でキーを合わせる／オクターブを上下する。
対象は童謡・唱歌・ポップスの簡易伴奏譜が中心。M0でモーツァルト級の楽譜が
音価97.8%だったことから、この層は**軽微な修正で実用になる**見込み。

### 5つの要望への対応

| 要望 | 対応 |
|---|---|
| カメラで取り込む | 撮影 → 四隅補正 → OMR（非同期・数分） |
| スマホで表示 | Verovio WASM で SVG 描画。ピンチズーム・ページめくり |
| 音を2度上げる | 移調スライダー。**ブラウザ内で即時**（サーバ不要） |
| オリジナル楽譜として保存 | 端末内(IndexedDB)を既定、クラウド同期は任意 |
| 印刷機に転送 | PDF生成 → OSの印刷機能(AirPrint/Mopria)。**直接転送は技術的に不可能** |
| （追加）修正エディタ | 拍子指定 → 音価 → 音高 の順に直す |
| （追加）音を奏でる | Tone.js + ピアノ音源。再生位置に合わせて音符が光る |

## 2. アーキテクチャ

```
┌─ PWA (React 18 + Vite + TypeScript)  ※既存クイズアプリと同構成 ─────────┐
│                                                                        │
│  撮影      <input capture> → OpenCV.js 四隅検出・台形補正・二値化       │
│  描画      Verovio WASM : MEI → SVG                                    │
│  編集      MEI の DOM を直接操作（SVGのIDと1対1で対応）                 │
│  移調      Verovio の transpose オプション ★サーバ不要・即時            │
│  再生      Tone.js Sampler + timemap で音符ハイライト同期               │
│  出力      SVG → PDF → OSの印刷ダイアログ                              │
│  保存      IndexedDB（既定） / Firestore+Storage（任意のクラウド同期）  │
└────────────────────────────────────────────────────────────────────────┘
                          ↓ 画像アップロード          ↑ MEI
┌─ Cloud Run (Python / Docker)  ※OMRのときだけ動く ──────────────────────┐
│  oemer 0.1.8 → MusicXML                                                │
│  music21 で正規化（拍子の補完・小節の割り直し・調号の整理）→ MEI        │
│  ⚠️ onnxruntime==1.19.2 / numpy<2 を固定（新しい版ではモデルが読めない） │
└────────────────────────────────────────────────────────────────────────┘
                          ↕
┌─ Firebase ─────────────────────────────────────────────────────────────┐
│  Auth（既存流用） / Storage（原譜画像・MEI） / Firestore（ジョブ状態）  │
└────────────────────────────────────────────────────────────────────────┘
```

**設計の要点**

- **サーバが要るのは OMR のときだけ。** 移調・再生・編集・PDF化はすべてクライアント完結。
  結果としてサーバ費用は「取り込んだページ数」にのみ比例し、遊んでいる間は一切かからない。
- **MEI を唯一の正とする。** MusicXML は入出力の橋渡しに限る。
  Verovio が SVG に振るIDが MEI のIDと完全一致する（M0で191/191を確認）ため、
  タップした音符から `getElementById` でデータを直接引ける。
- **再生は MIDI ファイルを流すのではなく、音符データから自前でスケジュールする。**
  こうするとテンポ変更・部分ループ・片手だけ再生・移調プレビューが追加実装なしで手に入る。

## 3. 画面構成

| # | 画面 | 内容 |
|---|---|---|
| 1 | **本棚** | 保存した楽譜の一覧。表紙は原譜のサムネイル |
| 2 | **撮る** | 撮影 → 四隅を指でドラッグ調整 → 補正プレビュー → 複数ページ追加 |
| 3 | **読み取り中** | 数分かかるため進捗表示。閉じても裏で進み、完了したら通知 |
| 4 | **なおす**（エディタ） | 上に原譜写真／下に認識結果。合わない小節を色で警告 |
| 5 | **ひらく**（ビューア） | 移調スライダー・再生・ページめくり・自動スクロール |
| 6 | **印刷** | 用紙サイズ・余白を選んで PDF 化 → OSの印刷へ |

### エディタ（画面4）の設計 — ここが製品の本体

M0の検証から、**直す順番そのものをUIで誘導する**のが最も効く。

**ステップ1: 拍子を決める**
拍子記号は100%脱落する。だが1つ指定するだけで**連桁が148音符分自動復活**し、見た目が激変する。
起動直後に「この曲は何拍子？」だけを大きく聞く。よく使う4/4・3/4・2/4・6/8をボタンで。

**ステップ2: 合わない小節を直す**
拍子が決まると、各小節の音価合計を検算できる。合わない小節を赤く表示し、
「ここ」ボタンで順に送る。M0で小節数が12→15にずれた問題は、これで可視化される。
修正は音符をタップ → 音価ボタン（全・2分・4分・8分・16分・付点）。

**ステップ3: 音を確かめる**
小節単位・フレーズ単位でループ再生。**耳で気づく誤りは目で探すより速い。**
だから再生機能はエディタより先に作る（M3 → M4 の順にする理由）。

**ステップ4: 音高を直す**
誤りは0〜10%と少ない。タップ → 上下ボタン、または♯♭ボタン。

原譜写真は常に画面に出し、**縦分割で上下に並べる**（横並びはスマホでは狭すぎる）。
分割位置はドラッグで変えられるようにする。

### ビューアと再生（画面5）

- **移調スライダー**: 半音単位で −12 〜 +12。動かした瞬間に再組版される（サーバ不要）
- **調の表示**: 「ハ長調 → ニ長調」と日本語で出す。半音数だけでは何調か分からない
- **異名同音の自動選択**: +1半音で「変ニ長調(♭5)」と「嬰ハ長調(♯7)」なら、
  調号の少ない前者を自動で選ぶ。M0で確認したとおり、指定を誤ると**♭10という演奏不能な調号**が出る
- **音域チェック**: オクターブ移動でピアノの実音域（MIDI 21〜108）を外れたら警告
- **再生**: 再生／停止、テンポ、部分ループ、右手だけ・左手だけ
- **音符ハイライト**: timemap の時刻と音を突き合わせ、鳴っている音符を光らせる。
  小節IDも取れるので自動スクロールも同時に実現できる

## 4. マイルストーン

各マイルストーンの終わりに必ず「動くもの」が残るように区切る。

### M1 — 骨組み ＋ 画像楽譜として完成させる
移調が無くても単体で使える状態を先に作る。ここが土台であり、保険でもある。

- `apps/score/` に Vite + React + TS の雛形（既存クイズアプリの構成を踏襲）
- Firebase Hosting に別サイトとして割り当て、Auth は既存を流用
- 撮影 → OpenCV.js で四隅検出 → 手動調整 → 台形補正 → 適応的二値化
- 複数ページの管理（並べ替え・削除）
- IndexedDB への保存、本棚画面
- 画像のまま PDF 化 → OSの印刷へ
- PWA 化（オフラインで本棚と閲覧が使える）

### M2 — OMRバックエンド
- Cloud Run 用 Dockerfile。**onnxruntime==1.19.2 / numpy<2 を固定**（新しい版ではモデルが読めない）
- 非同期ジョブ: 画像を Storage へ → ジョブ登録 → 完了を Firestore で通知
- oemer → MusicXML → music21 で正規化 → MEI を保存
- 1ページ5〜6分かかる前提のUI（閉じても裏で進む、完了通知）
- 失敗時のリトライと、はっきりしたエラー表示

### M3 — 表示・移調・再生
再生をエディタより先に作る。**耳で誤りに気づけると、修正作業の効率が段違いになる**ため。

- Verovio WASM の組み込み、MEI → SVG 描画
- ピンチズーム、ページめくり、横向き対応
- 移調スライダー＋調名の日本語表示＋異名同音の自動選択＋音域警告
- Tone.js Sampler ＋ ピアノ音源（数音おきのサンプルを補間、数MBに圧縮しPWAでキャッシュ）
- timemap を使った音符ハイライトと自動スクロール
- テンポ変更・部分ループ・片手再生

### M4 — 修正エディタ
- MEI の DOM 操作レイヤ（音高・音価・付点・臨時記号・音符の追加削除・元に戻す/やり直す）
- 拍子の指定 → 小節の割り直し → 連桁の自動生成
- 小節ごとの音価検算と、合わない小節の警告表示・順送り
- 原譜写真との上下分割ビュー（分割位置をドラッグ可能）
- 音符タップ → 選択 → 編集パレット（スマホの親指が届く位置に置く）

### M5 — 保存・整理
- 曲名・作曲者・タグ・フォルダ
- 原譜と移調版のバージョン管理（原譜は必ず残す）
- クラウド同期（**任意のオプトイン**。既定は端末内のみ）

### M6 — 公開準備
- 利用規約（自作曲・パブリックドメイン・自身が権利を持つ楽譜のみ、を明記）
- アップロード画面での著作権注意表示
- **共有・公開機能は作らない**（設計として持たない）
- 無料枠の上限設計と、超過分の課金導線（Stripe。クイズアプリの実装を流用）
- 特定商取引法に基づく表記、お問い合わせ（mailto）
- デザイン統一（クイズアプリと同じ「脱・AI感」の方針で、可愛くほんわかと）

## 5. コストと課金

M0実測: **1ページ 5〜6分、Cloud Run(2vCPU/4GB) 換算で約3円**。

クイズアプリと決定的に違う点として、**利用量がそのまま原価になる**。
移調・再生・編集・印刷はクライアント完結なので無料だが、取り込みだけは実費が出る。

| 案 | 内容 |
|---|---|
| 無料枠 | 月◯ページまで無料。それ以上は課金 |
| 買い切り | 取り込み◯ページ分のチケットを購入 |

どちらにするかは、公開直前（M6）に実際の利用傾向を見てから決めてよい。
M1〜M5の間は、なつみとテスターだけが使う想定で上限を設けておく。

## 6. 法務（一般公開のため必須）

市販楽譜を自分で撮って自分で使うのは私的複製（著作権法30条）の範囲だが、
**それをクラウドに保存する機能を事業者が提供すると、事業者が複製主体とみなされるリスク**がある
（まねきTV／ロクラクII 最高裁判決の法理）。以下は設計に織り込む。**後付けは効かない。**

- 保存の既定は端末内(IndexedDB)。クラウド同期は明示的なオプトイン
- **共有・公開機能を持たない**（URLで他人に見せられる導線を作らない）
- 利用規約とアップロード画面に、対象を自作曲・パブリックドメイン・自身が権利を持つ楽譜に限る旨を明記
- 開発とテストにはパブリックドメイン楽譜のみを使う（M0でも Mozart K545 / Joplin を使用）

## 7. リスクと、次に確かめること

| リスク | 影響 | 対応 |
|---|---|---|
| 実物の紙楽譜での精度が合成写真より低い | 大 | M2の早い段階で実物を撮って測り直す |
| 市販楽譜の版面（浄書フォントの違い）で精度が落ちる | 中 | 同上。落ちるなら対象を絞る |
| スマホ実機でのVerovio描画が遅い | 中 | M3の初期に実機で計測。遅ければページ分割を粗くする |
| エディタのスマホUIが使いづらい | 大 | M4は紙で操作を検討してから実装する |
| oemerの更新停止・依存の陳腐化 | 中 | Dockerでバージョンを完全固定。モデルもイメージに同梱 |

**未検証で、着手前に確かめたいこと**
- 実際の紙楽譜をスマホで撮った画像での精度
- 市販の楽譜（浄書フォントや版面が異なる）での精度
- 複数ページ・見開き撮影の扱い
- Verovio WASM のスマホ実機での描画速度
