# 楽譜カメラアプリ — M0 技術検証レポート

**検証日**: 2026-08-02
**目的**: 「ピアノの楽譜をカメラで取り込み、移調して、保存・印刷する」アプリが技術的に成立するかを、実装着手前に確かめる。
**結論**: **条件付きで成立する。ただし「撮ったら全自動で移調済み楽譜が印刷できる」は不可能。**

---

## 1. 検証の方法

「写真から音符データを読み取る」精度を客観的に測るため、**正解データを持つ楽譜**を人工的に用意した。

1. music21 の内蔵コーパスからピアノ曲を取得（＝正解の MusicXML）
2. Verovio で A4 に浄書し、200dpi の PNG にする（＝きれいな画像）
3. OpenCV で **台形歪み・照明ムラ・影・手ブレ・JPEG圧縮** を加え、スマホ撮影を再現（＝写真画像）
4. OMRエンジンに読ませ、出力 MusicXML を正解と機械的に突き合わせる

再現スクリプトは `apps/score/spike/` に置いた。

### テスト素材（いずれもパブリックドメイン）

| 名前 | 曲 | 難易度の理由 |
|---|---|---|
| mozart | K545 第1楽章 冒頭12小節 | ハ長調・臨時記号少・単純な大譜表 |
| joplin | Maple Leaf Rag 冒頭12小節 | 変イ長調(♭4)・密な和音・装飾音・反復記号 |

### 検証した構成

| 用途 | 採用 | 備考 |
|---|---|---|
| OMRエンジン | **oemer 0.1.8**（MIT） | Audiveris は高精度だが **AGPL** のため公開Webサービスでは避ける |
| 実行環境 | onnxruntime **1.19.2** + numpy **1.26.4** | ⚠️ onnxruntime 1.28 は `ConvTranspose` の負padでモデル読込に失敗。numpy 2.x も不可。**本番Dockerでバージョン固定が必須** |
| 楽譜操作 | music21 10.5 | 移調・調号変換・小節割り直し |
| 浄書・描画 | Verovio（WASM対応） | MusicXML→SVG/PDF/MIDI |
| PDF化 | cairosvg | SVGをベクタのままPDF化 |

## 2. 結果

### 2-1. 認識精度

| テスト | 音高 F1 | 音高+音価 F1 | 調号 | 拍子 | 強弱 | 反復 | 処理時間 |
|---|---|---|---|---|---|---|---|
| モーツァルト・きれいな画像 | 96.7% | 91.2% | ✅ | ❌脱落 | — | — | 351秒 |
| **モーツァルト・写真** | **100.0%** | **97.8%** | ✅ | ❌脱落 | — | — | 295秒 |
| ジョプリン・きれいな画像 | 94.0% | 73.7% | ✅ | ❌脱落 | ❌2→0 | ❌2→0 | 322秒 |
| **ジョプリン・写真** | **89.8%** | **74.1%** | ✅ | ❌脱落 | ❌2→0 | ❌2→0 | 377秒 |

音符数・パート数（左右の手）は4件すべて正解と一致。休符は過剰生成された（12個→18〜24個、21個→32〜36個）。

### 2-2. わかったこと

**① 写真の劣化は、思ったより問題ではない**
写真版はきれいな画像版と同等（モーツァルトではむしろ写真版が上）。精度を左右するのは**撮影品質ではなく楽曲の複雑さ**だった。前処理（台形補正・二値化）を作り込む価値はあるが、最優先ではない。

**② 音高は実用水準に達している**
90〜100%。「どの音か」はほぼ読める。

**③ リズムと記号類は実用水準に届かない**
音価まで含めると易しい曲で91〜98%、複雑な曲で**74%**まで落ちる。さらに**拍子記号は4件すべてで脱落**し、強弱記号・反復記号も全滅した。
**→ 自動認識の結果をそのまま印刷しても弾けない。人が直す工程は省略できない。**

**④ 連桁の消失は「認識ミス」ではなく「拍子記号の欠落」が原因**
oemer の出力は連桁が全く付かず読みにくいが、**拍子記号を1つ与えて小節を割り直すだけで、連桁が148音符分自動復活**し、楽譜らしい見た目に戻った（`samples/mozart_photo_fixed.jpg`）。
**→ 修正エディタで最初にやらせるべきは「拍子の指定」。1タップで見た目が激変する。**
ただし同時に、音価の誤りが**小節数のズレ**として顕在化した（12小節→15小節）。音価の修正からは逃げられない。

**⑤ 移調から印刷までは、技術的リスクなし**
ハ長調→**ニ長調（♯2つ）**へ調号ごと正しく変換され、トリル・スラー・途中の音部記号変更も保持したまま再組版できた（`samples/transposed_M2.jpg`）。写真→OMR→移調→PDF の一気通貫も成功（変イ長調→変ロ長調）。MIDI書き出しも動作したので、**移調後の音を耳で確認する機能**も作れる。

**⑥ 処理は重い — CPUで1ページ約5〜6分**
4vCPUで平均336秒。**同期処理は不可能**。ジョブ投入→完了通知の非同期設計が必須。
Cloud Run（2vCPU/4GB）換算で**1ページあたり約3円**。1人が10ページ取り込むと30円かかる。一般公開する場合、**クイズアプリと違って利用量がそのまま原価になる**ため、無料枠の上限設計か課金導線が必要。

### 2-3. 移調ロジックの落とし穴

「+1半音」をどう指定するかで結果が変わる。**半音数だけで移調してはいけない。**

| 操作 | 音程指定 | 結果 | 調号 |
|---|---|---|---|
| +1半音 | 増1度 (A1) | 嬰ハ長調 | ♯7 |
| +1半音 | 短2度 (m2) | 変ニ長調 | ♭5 |
| +2半音 | 長2度 (M2) | ニ長調 | ♯2 |
| +2半音 | 減3度 (d3) | （理論上） | **♭10 = 演奏不能** |

**→ UIは半音数で受け取り、内部で「読みやすい調」になる音程を自動選択する必要がある。** 変ニ長調(♭5)と嬰ハ長調(♯7)なら前者を選ぶ、という判断ロジックを必ず入れる。

またオクターブ移動では、ピアノの実音域（MIDI 21〜108）を超えないかの判定と、音部記号の切り替えが必要。

## 3. 結論と、計画への反映

### できること / できないこと

| 要望 | 判定 |
|---|---|
| カメラで取り込む | ✅ できる |
| スマホで表示 | ✅ できる |
| **音を2度上げる** | ✅ **できる（データ化さえ済めば確実）** |
| オリジナル楽譜として保存 | ✅ できる |
| 印刷機に転送 | ⚠️ PDF生成 → OSの印刷機能(AirPrint/Mopria)経由なら実現。ブラウザから直接プリンタへ送る手段は存在しない |
| **撮ってすぐ全自動で移調** | ❌ **できない。人による修正工程が必ず要る** |

### 製品としての現実的な形

> 撮る → 自動認識（数分・非同期） → **人が直す** → 移調 → 印刷

この「人が直す」エディタが、このアプリの本体になる。ここの作り込みが製品の成否を決める。

### 修正エディタの優先順位（検証結果から導いた順）

1. **拍子記号の指定** — 必須。1タップで連桁が復活し、見た目が激変する
2. **音価の修正** — 複雑な曲では26%が誤り。小節が合わない箇所をハイライトして誘導する
3. **音高の修正** — 誤りは0〜10%と少ない。頻度は低いが、間違うと致命的
4. 強弱・反復記号 — 全滅するが、演奏には影響が小さい。後回し可

**原譜の写真を常に横に並べて見比べられるUI**が必須。数値上は「小節が合わない」としか分からず、どちらが正しいかは原譜を見ないと判断できないため。

### 未検証・次に確かめるべきこと

- 実際の紙楽譜をスマホで撮った画像での精度（本検証は合成写真）
- 市販の楽譜（浄書フォントや版面が異なる）での精度
- 複数ページ・見開き撮影の扱い
- Verovio の WASM をスマホ実機で動かしたときの描画速度

## 4. 追加検証（エディタ・再生の要望を受けて）

修正エディタと音の再生を作ると決まったため、その前提となる3点を追加で確かめた。
検証スクリプトは `spike/editor_playback.py`。

### ① 画面の音符をタップして特定できるか → ✅

Verovio が出力する SVG の音符要素191個すべてに ID が振られ、**そのIDがデータ側(MEI)の音符IDと1対1で一致**した（191/191）。
SVG には `note` `rest` `chord` `measure` `staff` `layer` `beam` `slur` `clef` `accid` の各クラスも付く。

**→ タップした音符 → `getElementById` でデータ側の要素を直接引ける。エディタの土台として理想的。**
このため**内部データは MEI を正とする**のが最適。独自JSONに変換すると往復で情報が落ちるうえ、この対応関係を自前で維持する羽目になる。

### ② 再生位置に合わせて音符を光らせられるか → ✅

`renderToTimemap()` が **再生時刻(ms) → 発音する音符IDの配列** を返す。

```json
{"tstamp": 0, "qstamp": 0, "tempo": 132, "on": ["v1mx8dnx", "dx4oxzl"], "measureOn": "gqga4n1"}
```

小節のIDも含まれるため、**音符ハイライトと「今どの小節か」の自動スクロール**の両方が作れる。

### ③ 移調した楽譜を正しく鳴らせるか → ✅

移調後のMIDIを解析したところ、**全26種の音高がちょうど+2半音**（MIDI 43〜84 → 45〜86）で完全一致した。

### ④ 移調はブラウザだけで完結できるか → ✅ （設計上の大きな発見）

music21（サーバ側）を使わずとも、**Verovio 自体に `transpose` オプションがある**。
長2度・短3度・完全5度・オクターブのすべてで音高が正しく変換され、調号も**♯2つ（ニ長調）**として正しく描画された。トリル・スラーも保持される。

**→ 移調にサーバ往復は不要。スライダーを動かした瞬間に再組版でき、通信もサーバ費用も発生せず、オフラインでも動く。**
サーバ側の music21 は、OMR直後の正規化（拍子の補完、小節の割り直し）に用途を限定してよい。

### 追加検証を踏まえた技術選定

| 項目 | 決定 | 根拠 |
|---|---|---|
| 内部データ形式 | **MEI**（MusicXMLは入出力用） | SVGとIDが一致し、DOM操作で直接編集できる |
| 移調の実行場所 | **クライアント（Verovio WASM）** | サーバ往復ゼロ・即時プレビュー・オフライン可 |
| 再生方式 | **音符データから自前スケジュール**（MIDIファイル再生ではない） | テンポ変更・部分ループ・片手再生・移調プレビューが追加実装なしで手に入る |
| 音源 | Tone.js Sampler + 圧縮ピアノサンプル | 合成音は音が硬く、子供向けの世界観に合わない。数音おきのサンプルを補間すれば数MBに収まりPWAでキャッシュできる |

## 5. 追加検証（「撮った画像を移調したい」を受けて）

### ① Verovio はブラウザでそのまま動く → ✅（M3の設計が確定）

7MBのWASMバンドルを実機相当のブラウザで動かし、実測した。

| 項目 | 実測 |
|---|---|
| WASM初期化 | 177ms |
| 初回の浄書（8小節・122音符） | 176ms |
| **移調（9通りの平均）** | **61ms**（最速46ms／最遅97ms） |

**→ 移調はスライダーを動かした瞬間に組版し直せる。** timemap・MIDI・MEI出力もブラウザ側で取れた。
サーバは要らない。ただしバンドルが7MBあるため、PWAでキャッシュする前提にする。

（注意点: `verovio.module.onRuntimeInitialized` は 6.2.0 の UMD ビルドでは未定義。
`new verovio.toolkit()` が成功するまで短い間隔で試す必要がある。）

### ② ブラウザ内で動く自作OMR → 音の高さは読めるが、長さは読めない

サーバのOMR（oemer）はPython＋110MBのモデルで、ページからは呼べない。
そこで**このアプリ自身が作る「まっすぐな白黒ページ」限定**の軽量OMRを自作し、
M0と同じ正解データで測った。

| 項目 | 結果 |
|---|---|
| 五線の検出 | **8段／8段**（大譜表4段すべて） |
| 音高の再現率 | **92.1%** |
| 音高の適合率 | 69.0% |
| 音高のF1 | **78.9%** |
| 処理時間 | **約100〜300ms**（サーバ版は5〜6分） |
| 音価（長さ） | **読めない** |

効いた工夫は次の4つ。いずれも「符頭と、それ以外の記号との形の違い」を突いている。

1. **五線は黒画素の数ではなく「長く途切れない横の連なり」で探す** — 画素数で数えると、
   符頭や符尾が密な行と区別がつかず、5本の線が1つの帯に融合してしまう
2. **2段構えで探す** — 1回目は厳しく引いて線間を把握し、2回目は緩めて既知の線間で検証する。
   最終段は小節が少なく線が短いうえ、16分音符に寸断されて1回目のしきい値に届かない
3. **横に長く続くものを除く** — これがないと、16分音符の二重の梁が「梁・すきま・梁」で
   判定窓を埋めてしまい、梁に沿って偽の符頭が数珠つなぎに並ぶ（適合率18%まで落ちた）
4. **縦に長く続くものを除く** — 音部記号・小節線・符尾を弾ける

**限界**: 音価（音の長さ）は読めない。M0で学習済みモデルですら複雑な曲で74%だった箇所であり、
この方式では手が出ない。**したがって「移調した楽譜を組み直して印刷する」はまだできない。**

### ③ 到達した形

音の高さだけは信用できるので、それだけで成り立つ機能に絞った。

> 撮った楽譜の上に、**移調後に音符が来る位置**を重ねて描き、その音を鳴らす

五線上で音符が動く距離は半音数ではなく全音階の段数で決まるため、
半音数→段数の換算表（+2半音＝長2度＝1段、+3半音＝短3度＝2段…）を持たせている。
歌の伴奏でキーを合わせる用途には、この形でそのまま使える。

## 6. 実機で見つかった不具合と、その先にあった本当の原因

### ① 四隅の印がドラッグで動かない

**原因**: 印を動かすたびに `drawGuide()` が印そのものを作り直していた。
最初の1回動いた瞬間に、掴んでいる要素がDOMから消えて指から離れる。

**直し方**: 印は読み込み時に一度だけ作り、以後は位置（`style.left/top`）だけ更新する。
あわせて当たり判定を12px広げ、選んでから矢印キーでも動かせるようにした。

### ② その先にあった、もっと大きな問題 — わずかな傾き

ドラッグが正しく効くようになった結果、**四隅を正確に合わせられるようになったら
かえってOMRが壊れた**（五線の検出が 8段 → 0〜5段）。

調べると、五線は途切れていなかった。ある範囲では220画素すべてが連続して黒だった。
問題は**残った傾き**だった。

- 四隅を指で合わせる以上、1〜3度のズレは必ず残る
- 幅1290pxで0.5度傾くと、1本の五線が**11px＝1線間ぶん**も上下にずれる
- すると1本の線が複数の行にまたがり、「長く途切れない横の連なり」が消える
- 行ごとに見ると、線は200px程度の断片にしか見えなくなる

**直し方**: 五線を探す前に傾きを推定して直す。
列ごとに縦へずらしながら黒画素の縦方向の分布を作り、**分布がいちばん尖る傾き**を選ぶ
（±5度をざっと見てから、そのまわりを細かく）。符頭の座標は、元の写真に重ねて描けるよう
傾きを戻した値も持たせる。

⚠️ 推定関数では**縦方向を間引いてはいけない**。太さ1〜2画素の五線は、1行飛ばすだけで
丸ごと抜け落ちる。速さが要るなら列のほうを間引く。

### ③ 傾き補正の効果（4通りの切り取りで実測）

| 切り取り方 | 残っていた傾き | 五線 | 音高の再現率 | F1 |
|---|---|---|---|---|
| ぴったり | 0.80度 | 7/8 | 70.2% | 64.4% |
| 余白ひろめ | 0.41度 | **8/8** | **91.6%** | 74.9% |
| 余白せまめ | 0.94度 | **8/8** | 64.9% | 60.5% |
| 少しずれ | 3.09度 | 7/8 | 71.7% | 66.2% |

補正前は同じ4件が **0〜5段／再現率0〜64%** だった。処理時間は約430〜510ms。

### ④ あわせて直したこと

- 補正後の解像度を150dpi相当 → **200dpi相当**（A4を1654px）へ。五線が1px未満に潰れるのを防ぐ
- 白黒ページの保存を JPEG → **PNG**（可逆）へ。細い線がにじんで消えるのを避ける
- 二値化の「平坦な場所は紙とみなす」しきい値を 11 → 5 へ。白い紙の上の細い五線が
  平坦と判定されて破線状に千切れていた
- 五線のしきい値を**ページ幅基準から「いちばん長い五線」基準**へ。余白の取り方が
  変わっただけで検出が崩れていた
- 線間の代表値を中央値から**最頻値**へ。かすれて割れた線が作る細かい間隔に引きずられていた

### ⑤ この経験からの教訓

**入力の前処理が、認識アルゴリズムより先に効く。**
今回はアルゴリズムを何度も調整したが、効果が出たのは傾き補正・解像度・保存形式という
**認識より前の工程**だった。実装計画のM4（修正エディタ）に入る前に、
M2の前処理を実機の写真で詰めておくほうが順序として正しい。
